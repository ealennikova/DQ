\# Проект Data Quality для IoT / wearable data



Автоматизированный контроль качества данных о физической активности и сне пользователей с использованием Python, PostgreSQL, Apache Airflow и Soda Core.



\## 1. Цель проекта



Цель — построить воспроизводимый процесс Data Quality, который автоматически выявляет критические ошибки и предупреждения до передачи данных в аналитические и downstream ML-процессы.



Основной принцип:



\*\*загрузка данных → автоматические DQ-проверки → фиксация результата → мониторинг → обработка инцидентов\*\*



\## 2. Данные



В проекте используются два CSV-источника с данными о физической активности и сне пользователей.



После объединения:



\- 1 955 записей;

\- 13 полей;

\- 2 источника;

\- бизнес-ключ: `Id + ActivityDay`.



Основные группы показателей:



\- пользователь;

\- дата;

\- физическая активность;

\- шаги;

\- калории;

\- сон.



\## 3. Результаты profiling



Было определено 9 DQ-контролей.



| Правило | Измерение | Результат | Критичность |

|---|---|---:|---|

| DQ-01 | Id заполнен | 100,00% | Critical |

| DQ-02 | Корректная дата | 100,00% | Critical |

| DQ-03 | Уникальность Id + ActivityDay | 97,95% | Critical |

| DQ-04 | Неотрицательные значения | 100,00% | Critical |

| DQ-05 | Согласованность activity minutes | 100,00% | Critical |

| DQ-06 | minutes\_instances <= 1440 | 100,00% | Critical |

| DQ-07 | Полное суточное покрытие | 96,73% | Warning |

| DQ-08 | Согласованность sleep metrics | 99,90% | Warning |

| DQ-09 | Полнота sleep metrics | 99,39% | Warning |



\### Основная проблема



После объединения источников обнаружено:



\- 20 конфликтующих бизнес-ключей;

\- 40 затронутых записей;

\- разные значения для одного `Id + ActivityDay`.



Это создаёт риск двойного учёта и искажения аналитических показателей.



\## 4. Автоматизация



Реализованный pipeline:



```text

CSV

&#x20;↓

PostgreSQL

&#x20;↓

Apache Airflow

&#x20;↓

Soda Core

&#x20;↓

DQ checks

&#x20;↓

dq\_checks\_log

&#x20;↓

Dashboard / Incident Management



Airflow pipeline содержит две основные задачи:



load\_activity\_data — загрузка данных;

run\_soda\_checks — выполнение DQ-проверок.



Soda Core выполняет 9 проверок и сохраняет результаты в журнал dq\_checks\_log.



Автоматизированный pipeline был успешно запущен и результаты проверок зафиксированы в журнале.



5\. Интерпретация результатов

Critical



Критические нарушения требуют блокировки, изоляции или расследования до передачи данных downstream.



К ним относятся:



отсутствие идентификатора;

некорректная дата;

нарушение уникальности;

отрицательные значения;

нарушение арифметической согласованности;

превышение допустимого количества минут.

Warning



Предупреждения не обязательно блокируют загрузку, но должны фиксироваться и мониториться:



неполное суточное покрытие;

отдельные нарушения sleep metrics;

неполнота связанных sleep-показателей.



В текущем наборе обнаружено:



1 Critical FAIL и 3 Warnings.

8\. 152-ФЗ



Если Id позволяет прямо или косвенно идентифицировать физическое лицо, данные могут подпадать под требования Федерального закона №152-ФЗ.



DQ-контроль должен как минимум включать контроль:



заполненности идентификатора;

уникальности;

допустимого формата;

целостности;

изменений;

качества при передаче между системами.



DQ-проверки снижают риски качества и целостности данных, но сами по себе не обеспечивают соответствие требованиям 152-ФЗ.

11\. Ограничения



В рамках проекта не определялся автоматический приоритет источников и не выполнялось автоматическое разрешение конфликтов между источниками.



Это является следующим этапом Data Governance.



Также не используется проверка TotalMinutesAsleep <= MinutesInBed как DQ-ошибка, поскольку семантика этих показателей в исходном наборе недостаточно определена для безопасного бизнес-правила.



12\. Итог



Проект переводит контроль качества данных из разовой ручной проверки в воспроизводимый автоматизированный процесс.



Основная ценность:



раннее обнаружение проблем → снижение риска ошибочной аналитики → прозрачность качества → управляемость данных → возможность масштабирования.
