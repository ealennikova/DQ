# Стратегия и план внедрения

## 1. Цель проекта

Цель проекта — построить автоматизированный контроль качества IoT / wearable data, который позволяет обнаруживать критические ошибки и предупреждения до передачи данных в аналитические и downstream ML-процессы.

Основной принцип:

**Качество данных должно контролироваться автоматически на этапе загрузки и после интеграции источников.**

## 2. Результаты profiling

В исследовании использовано:

- 2 источника данных;
- 1 955 записей после объединения;
- 13 полей;

- 9 DQ-контролей.

Основные результаты:

## 3. Бизнес-эффект

Нарушение уникальности после интеграции может привести к:

- двойному учёту данных;
- искажению ежедневных показателей;
- ошибкам аналитических отчётов;
- снижению качества ML-моделей;
- неверной интерпретации пользовательской активности и сна.

Ключевой вывод: структурно корректные данные не гарантируют бизнес-корректность после интеграции.

## 4. Предлагаемая архитектура

Текущий автоматизированный процесс:

**CSV → PostgreSQL → Apache Airflow → Soda Core → DQ checks → dq_checks_log**

### Этапы

1. загрузка данных в PostgreSQL;
2. запуск Airflow pipeline;
3. выполнение Soda Core checks;
4. фиксация результатов;
5. запись результатов в `dq_checks_log`;
6. визуализация качества данных;
7. расследование критических нарушений.

В Airflow реализованы задачи:

- `load_activity_data`;
- `run_soda_checks`.

## 5. Классификация результатов

### Critical

Критические нарушения блокируют или отправляют данные на дополнительное расследование.

К ним относятся:

- отсутствие идентификатора;
- некорректная дата;
- нарушение уникальности бизнес-ключа;
- отрицательные значения;
- нарушение арифметической согласованности;
- превышение 1440 минут наблюдения.

### Warning

Предупреждения не обязательно блокируют загрузку, но требуют мониторинга:

- неполное суточное покрытие;
- неполная информация о сне;
- отдельные нарушения согласованности sleep metrics.

## 6. Мониторинг

Результаты проверок сохраняются в таблицу `dq_checks_log`.

Основные поля:

- `table_name`;
- `check_name`;
- `check_status`;
- `result_type`;
- `result_value`;
- `create_timestamp`.

Это позволяет хранить историю запусков и анализировать повторяющиеся проблемы качества.

Dashboard показывает:

- количество записей;
- количество DQ-правил;
- количество Critical и Warning правил;
- PASS / FAIL / WARNING;
- долю успешных проверок;
- количество нарушений;
- основные выявленные проблемы.

## 7. Data Governance

Для устранения основной проблемы необходимо формализовать:

1. владельца данных;
2. владельца DQ-правил;
3. приоритет источников;
4. правила разрешения конфликтов;
5. source/data lineage;
6. ответственность за исправление данных;
7. процесс обработки критических DQ-инцидентов.

Для каждого критического нарушения должен существовать понятный процесс:

**обнаружение → уведомление → расследование → исправление/изоляция → повторная проверка → закрытие инцидента.**

## 8. Data Contract

Для набора определён Data Contract, включающий:

- бизнес-ключ;
- структуру данных;
- типы полей;
- ограничения значений;
- DQ-правила;
- критичность;
- действия при нарушении.

Критические проверки должны выполняться до передачи данных downstream.

## 9. 152-ФЗ и защита персональных данных

Если `Id` позволяет прямо или косвенно идентифицировать физическое лицо, данные могут подпадать под требования Федерального закона №152-ФЗ.

С точки зрения DQ минимально необходимы:

- контроль заполненности идентификатора;
- контроль уникальности;
- контроль допустимого формата;
- контроль целостности данных;
- аудит изменений;
- контроль качества при передаче данных между системами.

DQ-контроль снижает риски, связанные с качеством и целостностью данных, но сам по себе не является подтверждением соответствия требованиям 152-ФЗ.

## 10. Сценарий экономического эффекта

Для оценки эффекта используется сценарная модель.

Предположим, что ручная проверка и расследование DQ-проблем требует около **320 USD в месяц**, а автоматизированный контроль снижает затраты до **160 USD в месяц**.

Потенциальный эффект:

- экономия: **160 USD / месяц**;
- потенциальная экономия: **1 920 USD / год**.

Это сценарная оценка, а не фактическая финансовая отчётность.

Дополнительный эффект связан с предотвращением ошибок аналитики и downstream ML, стоимость которых может превышать непосредственные затраты на ручную проверку.

## 11. План внедрения

### Этап 1 — автоматизация контроля

- формализовать DQ-правила;
- перенести проверки в Soda Core;
- запускать проверки через Airflow;
- сохранять результаты в DQ log.

### Этап 2 — мониторинг

- хранить историю запусков;
- настроить dashboard;
- настроить уведомления по Critical нарушениям;
- анализировать динамику проблем.

### Этап 3 — Data Governance

- назначить владельцев данных;
- формализовать Data Contract;
- определить source priority;
- определить правила conflict resolution;
- внедрить data lineage.

### Этап 4 — масштабирование

Распространить подход на новые источники и наборы данных:

**source → contract → profiling → DQ rules → automated checks → monitoring → incident management**

## 12. Критерии успеха

Проект считается успешным при выполнении следующих условий:

- критические DQ-проверки выполняются автоматически;
- результаты каждого запуска сохраняются;
- критические нарушения обнаруживаются до downstream-потребления;
- для конфликтов источников существует процедура разрешения;
- DQ-правила имеют владельцев;
- новые проверки можно добавлять без перестройки всей системы.

## 13. Итог

Проект переводит контроль качества данных из разовой ручной проверки в воспроизводимый автоматизированный процесс.

Основная ценность для бизнеса:

**раннее обнаружение проблем → снижение риска ошибочной аналитики → прозрачность качества → управляемость данных → возможность масштабирования.**
