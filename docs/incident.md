# Инцидент качества данных

## ID инцидента

**DQ-INC-001**

## Тип инцидента

**Дублирование / конфликт бизнес-ключей**

## Связанное DQ-правило

**DQ-03 — уникальность `Id + ActivityDay`**

## Критичность

**Critical**

## Статус

**Открыт / расследование**

## 1. Описание инцидента

В ходе автоматизированной проверки качества объединённого набора IoT / wearable data было выявлено нарушение уникальности бизнес-ключа `Id + ActivityDay`.

Объём набора данных — 1 955 записей.

DQ-проверка выявила:

- 20 конфликтующих бизнес-ключей;
- 40 затронутых записей;
- доля записей без нарушения уникальности — 97,95%.

Нарушение автоматически обнаружено Soda Core в Apache Airflow pipeline.

## 2. Обнаружение

Процесс:

**Загрузка данных → Airflow → Soda Core → журнал DQ**

Результат:

**DQ-03 Id + ActivityDay is unique**

- Нарушения: 40
- Статус: FAIL

Результат сохраняется в `dq_checks_log`.

## 3. Бизнес-влияние

Возможные последствия:

- двойной учёт;
- некорректные ежедневные показатели;
- искажение аналитики активности и сна;
- ошибки агрегированных отчётов;
- снижение достоверности downstream ML/аналитических моделей.

Основной риск — разные значения для одной логической дневной записи.

## 4. Результаты расследования

Два файла пересекаются по 2016-04-12. Одинаковые `Id + ActivityDay` присутствуют в обоих источниках, значения различаются.

При этом отсутствуют:

- приоритет источников;
- правила разрешения конфликтов;
- эталонный источник для показателя.

Поэтому конфликт нельзя безопасно устранить простым удалением дублей.

## 5. Предполагаемая первопричина

Отсутствует формализованный процесс согласования данных при пересечении источников.

Не определены:

1. приоритизация источников;
2. правила разрешения конфликтов;
3. хранение информации об источнике;
4. обязательная проверка уникальности после интеграции.

Записи могут быть структурно корректны, но создавать бизнес-нарушение после интеграции.

## 6. Корректирующие действия

### Немедленные

1. определить все 20 конфликтующих ключей;
2. сравнить значения;
3. определить достоверный источник;
4. исправить или изолировать конфликтующие записи;
5. повторно выполнить DQ-03.

### Предупреждающие

1. определить приоритет источников;
2. внедрить source/data lineage;
3. формализовать правила разрешения конфликтов;
4. выполнять uniqueness check после интеграции;
5. настроить уведомление при нарушении DQ-03;
6. не передавать неразрешённые критические конфликты downstream.

## 7. Критерии закрытия

- все 20 ключей проверены;
- источник определён;
- записи исправлены или изолированы;
- DQ-03 = 0;
- формализовано правило разрешения конфликтов.

## 8. Вывод

Одной schema validation недостаточно: оба источника могут быть структурно корректны, но после интеграции возникают бизнес-конфликты.

Поэтому DQ-контроль должен выполняться и после интеграции данных и включать проверки uniqueness, consistency и reconciliation.
